# セキュリティ診断（T-503）

2026-11-21、`feature/p5` 時点のコードと検証環境（tamacat-httpd 1.7 + Tomcat Secure Embed 11.0.29、Zabbix 6.0 / 7.0 / 8.0 の検証用コンテナ）で実施。外部の診断ツールではなく、設計書 6 章の方針に沿ったコードレビューと、稼働中のコンテナへの手動の試験による。

## 結果の概要

| 区分 | 結果 |
|---|---|
| 発見して修正したもの | 3 件（下記 F-1〜F-3） |
| 問題なし | 認証・セッション・CSRF・応答ヘッダ・認可（スコープ）・SQL 組み立て・エラー応答・依存ライブラリ |
| 未実施 | Maven 依存の CVE 自動照合（OWASP Dependency-Check は NVD の取得が必要なため）。外部の DAST ツール |

## 修正したもの

### F-1 X-Forwarded-For の先頭を信頼していた（中）
- 内容：ループバックからの要求では `X-Forwarded-For` の**先頭**を接続元として監査ログとログイン記録に使っていた。同じホストのリバースプロキシ（nginx の `proxy_add_x_forwarded_for` など）は値を**末尾に追加**するので、先頭は利用者が送った値になり、接続元を偽れる。
- 修正：末尾（信頼するプロキシが追加した値）を使う（`WebSession.clientIp`）。
- 補足：現在の構成（tamacat-httpd 内蔵の Tomcat が接続を直接受ける）では接続元はソケットの値で、この経路は通らない。

### F-2 接続元ごとのログイン失敗制限がなかった（中）
- 内容：アカウントごとのロック（5 回失敗で 15 分）だけで、1 つの接続元から多数のアカウントに少しずつ試す攻撃（パスワードスプレー）を止められなかった。`login_attempts` に接続元は記録していたが使っていなかった。
- 修正：接続元ごとに、直近 15 分の失敗が 20 回以上なら、パスワードを照合せずに拒否する（応答は通常の失敗と同じ、処理時間も同等）。`TMON_SECURITY_MAX_LOGIN_FAILURES_PER_IP`（0 で無効）、`TMON_SECURITY_IP_WINDOW_SECONDS` で変更できる。既存の索引 `ix_login_attempts_ip` を使う。`UserServiceTest.clientAddressIsThrottledAcrossAccounts` で確認。

### F-3 JDBC URL の証明書ストア URL に任意の URL を指定できた（低）
- 内容：Zabbix DB の JDBC URL で許可している `trustCertificateKeyStoreUrl` に `http://...` を指定すると、MySQL ドライバがその URL を取得する（サーバーから任意の宛先への要求。システム管理者だけが設定できる）。
- 修正：`file:` のローカルファイルだけを許可し、`..` を含む値は拒否する（`JdbcUrlPolicy`）。

## 問題がなかった項目

| 項目 | 確認内容 |
|---|---|
| パスワード | PBKDF2-HMAC-SHA256 60 万回。存在しないユーザー・ロック中でもダミーの照合を行い、応答時間で区別できない。応答は失敗理由によらず `error.login` のみ |
| セッション | ログイン時にセッション ID を変更（固定化対策）。Cookie は `HttpOnly; SameSite=Strict`（本番は `Secure`）。30 分で失効。利用者は要求ごとに DB から読み直し、無効化・ロック・権限変更が即時に効く |
| CSRF | 状態を変える要求（ログイン・ログアウトを含む）はトークン必須。トークンなしのログアウトは 403 を確認 |
| 応答ヘッダ | CSP（インライン script なし）、`X-Frame-Options: DENY`、`nosniff`、`Referrer-Policy`、`Permissions-Policy`、`Cache-Control: no-store`。TRACE は 405 |
| 認可（スコープ） | 閲覧者（2 グループのみ許可）で確認：許可外サーバー・ホスト・アイテムの参照は 404、範囲外ホストのアイテム一覧は 0 件、管理者用 API（ユーザー・サーバー設定・アクション）は 403、更新・削除は 403 / 404 |
| SQL | すべてバインド変数。識別子は許可リスト（`IdentifierRules`）。LIKE はエスケープ。スコープ条件も ID をバインドする |
| エラー応答 | 例外はメッセージキーに変換し、スタックトレース・SQL を返さない。`WEB-INF` やパス横断は 404 |
| 秘密情報 | Zabbix DB のパスワードは AES-256-GCM（列名とサーバー ID を付加データに使用）。API から返さない。ログでマスク |
| Zabbix DB 接続 | URL の許可リストに加え、`allowLoadLocalInfile=false` などの防御用プロパティを常に指定 |
| 依存ライブラリ | 実行時に WAR へ入るのは jakarta.json-api 2.1.3、parsson 1.1.9、JSTL 3.0.x、mysql-connector-j 26.7.0 のみ。UI は `npm audit --omit=dev` で 0 件 |
| 書き込みの安全策 | 書き込み用 DB ユーザーは必要な表・操作だけの GRANT（`GrantsTest` で他の表に書けないことを確認）。プレビュー（実行してロールバック）、楽観的競合検出、監査ログ |

## 追加（P6）

- 2 段階認証（TOTP）を追加。パスワードが正しくてもコードの入力までは未認証のまま（`/api/me` などは 401）。コードは一度だけ有効で、誤りはアカウントのロック回数に数える。リカバリーコードはハッシュだけを保存。QR コードはブラウザ内で生成し、秘密鍵を外部サービスに送らない。UI の依存に `qrcode-generator` 2.0.4（MIT、依存なし）を追加（`npm audit` 0 件）。
- 検証：API で設定 → ログイン（コードなしでは保護 API が 401、誤ったコードは拒否、同じコードの再利用は拒否）→ リカバリーコード（1 回限り）→ 管理者によるリセット、をコンテナで確認。

## 追加（P8）

- パスキー（WebAuthn）を追加。検証は Java 標準の暗号機能だけの自前実装で、ソフトウェア認証器による単体テスト（3 アルゴリズムの登録・認証、チャレンジ・オリジン・RP ID・ユーザー検証・cross-origin・署名・カウンター・不正な CBOR の拒否）と、ブラウザーに組み込んだテスト用認証器による画面からの通し確認（登録、パスキーだけのサインイン、ユーザー検証なしの拒否、パスワード後の 2 段階目、パスワード付きの削除）を行った。
- パスキーだけのサインインはユーザー検証必須。応答は理由によらず同じエラーで、失敗は接続元ごとの制限に数える。登録・削除には現在のパスワードが必要（セッションを奪われてもパスキーを追加されない）。
- RP ID とオリジンは設定値だけを使い、リクエストの Host ヘッダーからは決めない。

## 運用上の注意

- 本番では HTTPS を終端し、`TMON_SESSION_COOKIE_SECURE=true`（既定）のままにする。
- リバースプロキシを置く場合は同じホスト（ループバック）から接続し、`X-Forwarded-For` に接続元を追加させる。
- Zabbix DB の参照用ユーザーには `SELECT` だけを与える（`grants/mysql.sql`）。
- 管理者アカウントでは 2 段階認証またはパスキーを使うことを推奨する。
- パスキーを使うときは `TMON_WEBAUTHN_RP_ID` に tamacat-monitor の URL のホスト名、`TMON_WEBAUTHN_ORIGINS` に利用者がアクセスするオリジンを設定する（HTTPS 必須。localhost は例外）。
